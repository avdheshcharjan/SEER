# Building a Social Micro Prediction Market on Base (15-Day Plan)

## Project Overview and Goals

We aim to build a **social micro prediction market** – essentially _“Tinder for prediction markets”_. Users can swipe right to **bet “Yes”**, swipe left to **bet “No”**, or swipe up to **skip** a prediction. This swipe-based UX makes participation as quick and fun as using a dating app. The platform will cover a wide range of categories – **crypto prices, sports outcomes, politics, tech trends, celebrities**, and more. Crucially, users can **create their own prediction markets**, enabling hyper-local or niche questions alongside global events. Each prediction question is a short-lived market where users stake real value on outcomes.

Key goals and features include:

- **Real Stakes with USDC:** Bets use **real USDC stablecoin on Base mainnet**, so outcomes have tangible rewards. Using a stablecoin ensures low volatility for bettors.
- **Easy Wallet Onboarding:** Users simply connect an Ethereum wallet (e.g. MetaMask or Coinbase Wallet) to start betting. No separate account creation – just a wallet connect and you’re in.
- **Mobile-First Mini-App:** The interface is designed mobile-first, potentially deployed as a **Farcaster Mini App** for seamless integration. This means the dApp can run inside the Base/Farcaster social app without a separate browser, offering a **native-like experience**[\[1\]](https://docs.base.org/mini-apps/quickstart/new-apps/install#:~:text=A%20mini%20app%20is%20a,App%20using%20the%20MiniKit%20template).
- **Fast, Gas-Efficient Network:** We choose **Base (an Ethereum L2)** as the deployment network for low fees and quick transactions. Base’s environment is EVM-compatible (easy smart contract deployment) and **user-friendly with built-in account abstraction features**.
- **Oracle-Based Settlement:** Each market will be resolved by an **oracle** to determine the winning outcome. This could be a trusted oracle service or a community-driven resolution mechanism – ensuring that when the real-world outcome is known, the smart contracts can settle the bets correctly.
- **Aggressive 15-Day Timeline:** We have only 2 weeks to build and deploy, so we will heavily leverage existing frameworks and libraries. The focus is on **assembling proven components** (rather than reinventing the wheel) and integrating them with a polished front-end. Gnosis’s Conditional Token Framework (CTF) will provide the backbone for market logic, drastically reducing development time.

This project takes inspiration from existing blockchain prediction markets like **Omen** and **Polymarket**, but adds a unique social UX. Just as Omen allows anyone to create and bet on markets with a custom oracle[\[2\]](https://blog.kleros.io/a-good-omen-kleros-x-gnosis-x-dxdao-align-with-conditional/#:~:text=In%20prediction%20markets%2C%20individuals%20stake,to%20resolve%20a%20market%E2%80%99s%20outcome), our platform empowers user-generated questions in a more casual swipe format. By the end of the 15 days, we expect to have a working MVP on Base mainnet where users can **browse a feed of prediction questions and swipe to place bets in a couple of taps**.

## Tech Stack and Key Components

To achieve this quickly, we will use a robust stack of **Web3 frameworks and services**. Below are the key technical components and choices:

- **Base Network (L2):** Base is an Ethereum Layer-2 known for low fees and developer-friendly tooling. It supports Ethereum smart contracts and even has native support for **account abstraction** (ERC-4337) via Coinbase’s developer platform. Transactions on Base cost only fractions of a cent, which is ideal for micro bets. Moreover, Base provides a Paymaster service to sponsor gas (more on that later)[\[3\]](https://docs.base.org/cookbook/go-gasless#:~:text=Base%20transaction%20fees%20are%20typically,The%20Paymaster%20allows%20you%20to). Deploying on Base mainnet ensures real economic value (USDC) is used, but with far cheaper gas than Ethereum mainnet.
- **USDC Stablecoin:** We will use **USDC on Base** as the currency for wagers. USDC is a reliable, liquid stablecoin pegged to USD, so users are betting with a currency that doesn’t fluctuate. [\[4\]](https://help.coinbase.com/en/coinbase/getting-started/crypto-education/usd-base-coin#:~:text=USD%20Base%20Coin%20,the%20time%20of%20mainnet%20launch). Using USDC means winners can withdraw a stable value and not worry about crypto volatility affecting their winnings.
- **Gnosis Conditional Token Framework (CTF):** This is the core smart contract framework that **tokenizes prediction outcomes**[\[5\]](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=Exploring%20the%20Gnosis%20Conditional%20Token,Based%20Prediction%20Markets). Gnosis CTF provides an ERC-1155 based **ConditionalTokens** contract that represents each prediction outcome as a token. For a given yes/no question, the framework will create two outcome tokens (e.g. “Yes shares” and “No shares”). Users buy these tokens when they bet, and can trade or hold them until resolution. The framework elegantly handles the math of splitting a stake into outcome tokens and later **redeeming winning tokens for payout**. It also supports more complex conditional logic (like combinatorial markets), though for our MVP we will stick to simple markets (each condition = one question). Gnosis has battle-tested these contracts; they’re even deployed on Ethereum mainnet[\[6\]](https://github.com/gnosis/conditional-tokens-contracts#:~:text=The%20conditional%20tokens%20contracts%20are,deployed%20at%20the%20following%20addresses), so we can reuse the code with confidence. We’ll deploy the ConditionalTokens contract to Base if not already available. To create a new prediction market, we’ll call the **prepareCondition(oracle, questionId, outcomeCount)** function on this contract[\[7\]](https://conditional-tokens.readthedocs.io/en/latest/developer-guide.html#:~:text=Before%20conditional%20tokens%20can%20exist%2C,used%20to%20prepare%20a%20condition)[\[8\]](https://conditional-tokens.readthedocs.io/en/latest/developer-guide.html#:~:text=Parameters%3A). That registers a new event (question) identified by a questionId (which could be a hash or ID of the question) and ties it to an oracle address responsible for reporting the result. Under the hood, this sets up an internal **conditionId** and an empty payout vector for that event, and emits a ConditionPreparation event. At this point, outcome tokens can be created and traded.
- **Automated Market Maker (AMM) for Prediction Markets:** To make the markets interactive and **allow users to bet at any time by buying outcome tokens**, we’ll use Gnosis’s **conditional market maker contracts**. Gnosis offers two AMM models – **Constant Product Market Maker (CPMM)** and **Logarithmic Market Scoring Rule (LMSR)**[\[9\]](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=Gnosis%20offers%20two%20market%20makers%3A)[\[10\]](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=Initially%2C%20LMSR%20was%20a%20pricing,of%20that%20outcome). For simplicity and familiarity, we can choose the **CPMM**, which works like Uniswap’s x_y=k formula. In a CPMM pool, the reserve of “Yes” tokens and “No” tokens is adjusted with each trade such that their product remains constant_[_\[11\]_](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=CPMM)_. This yields a real-time price/probability for each outcome: if many people are buying “Yes”, its price (implied probability) goes up, and “No” goes down. The math for CPMM is straightforward (no logarithms), making it easier to implement and reason about. Gnosis has a contract called_ _FixedProductMarketMaker.sol_ _(often used in Omen) which implements this logic_[_\[12\]_](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=Framework)_. We will leverage that contract (and its factory if needed) from the Gnosis_ _conditional-tokens-market-makers_ _repository. Using an AMM means we don’t need an orderbook or direct peer-to-peer betting; anyone can bet at the current odds, and the smart contract ensures liquidity. This approach was proven by Omen, which_ _used an automated market maker to match trades so that markets always reflect the latest odds_\*[\[13\]](https://blog.kleros.io/a-good-omen-kleros-x-gnosis-x-dxdao-align-with-conditional/#:~:text=Unlike%20other%20blockchain,expert%20opinion%20on%20their%20topic). We’ll deploy a FixedProductMarketMaker on Base and pair it with the ConditionalTokens contract and USDC collateral. Each new prediction market could be an instance of the AMM bound to a specific condition (question) and collateral (USDC).
- **Oracle for Outcome Resolution:** An oracle mechanism is essential to feed real-world results into the smart contracts. When the event outcome is determined (e.g. the game is over, or the election result is announced), the oracle will call the ConditionalTokens contract to report the outcome. Gnosis CTF leaves the oracle choice open – any address can be the oracle for a condition[\[14\]](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=of%20hashing%20three%20parameters%3A). For the MVP, we will use Uma:
- An approach is to use **UMA’s Optimistic Oracle**, which Polymarket used on Polygon. Polymarket’s implementation demonstrates that at market creation, you specify an oracle (UMA in their case) to handle resolution[\[15\]](https://medium.com/@abiodun.toluwanii/my-polymarket-revelation-diving-into-conditional-token-frameworks-and-if-this-then-that-on-the-b410c49c2187#:~:text=And%20here%E2%80%99s%20something%20else%20that%E2%80%99s,lose%20a%20lot%20of%20money). UMA allows a proposed outcome to be submitted and can be disputed if wrong, with financial incentives for honesty.

What’s important is that the architecture supports having an oracle address per market and using that to call the resolution on-chain. This ensures the platform can support any kind of question – you just need to assign an oracle that will know the answer.

- **Farcaster Base Mini App Integration:** We intend the dApp to be a **Farcaster Mini App**, which means it’s a web app that can launch directly inside Farcaster’s social client (Base app)[\[1\]](https://docs.base.org/mini-apps/quickstart/new-apps/install#:~:text=A%20mini%20app%20is%20a,App%20using%20the%20MiniKit%20template). We will use **Next.js** along with Base’s **MiniKit** tooling to scaffold the app quickly. The Farcaster integration offers some huge benefits:
- The app can be discovered and shared in the Farcaster social feed, increasing adoption. Users could share a prediction to their timeline, and others can click it and instantly start swiping/betting _without leaving the social app_.
- Base’s mini app environment likely provides a **wallet context** (the Base app has an in-app wallet or can pass the user’s Ethereum address through). This means a smoother login – possibly the user won’t even need to explicitly connect a wallet if they’re already logged in to Base app. We will still implement a standard Web3 wallet connect as fallback for those accessing via a normal browser.
- Using the Base mini app framework, we get some pre-built components and guidelines (the Base docs have manifest, context, etc.) which accelerates development. For example, authentication can use the Farcaster identity or an Ethereum message signature provided by the Base app.

In summary, by combining **Gnosis’s ready-made contracts** for conditional tokens and AMMs, the **Base network’s user-friendly infrastructure**, and a **modern mobile web frontend**, we have a solid stack that can be built in a short time. Now, let’s break down the implementation details for each part.

# PHASE 1: Smart Contracts Implementation
## Smart Contracts Implementation (Gnosis Conditional Tokens on Base)

**1\. Deploying the Conditional Tokens Contract:** We will start by deploying Gnosis’s ConditionalTokens.sol contract onto Base. This contract (ERC-1155) manages the creation of outcome tokens and the core logic of condition preparation and resolution[\[17\]](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=The%20logic%20of%20conditional%20tokens,is%20implemented%20in%20this%20repository)[\[18\]](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=First%20and%20foremost%2C%20let%E2%80%99s%20talk,its%20possible%20outcomes%20as%20outcomes). Gnosis’s repository provides this contract and it’s well-documented. On Ethereum mainnet, Gnosis has already deployed an instance at address 0xC59b0e4De5F1248C1140964E0fF287B192407E0C[\[6\]](https://github.com/gnosis/conditional-tokens-contracts#:~:text=The%20conditional%20tokens%20contracts%20are,deployed%20at%20the%20following%20addresses), but on Base we’ll deploy our own instance (using the same code). Once deployed, we’ll have the **base layer to create prediction events**: - To create a market (prediction question), our platform (or a user through our UI) will call ConditionalTokens.prepareCondition(oracleAddress, questionId, outcomeCount). For a **binary (Yes/No) market**, outcomeCount = 2. The questionId can be a unique hash for the question – perhaps the hash of the question text or an incrementing ID. The **oracleAddress** is the Ethereum address that will later report the result. After calling this, the contract emits an event and internally tracks the condition. No tokens are created yet in users’ hands, but it establishes the “event” in the system[\[8\]](https://conditional-tokens.readthedocs.io/en/latest/developer-guide.html#:~:text=Parameters%3A). - The contract uses those three parameters (oracle, questionId, outcome count) to derive a unique conditionId (via keccak256 hash)[\[19\]](https://conditional-tokens.readthedocs.io/en/latest/developer-guide.html#:~:text=Parameters%3A). This conditionId will identify the market going forward. It also sets up storage for the eventual outcome (payout array, initially empty) associated with that condition. - **Collateral and outcome tokens:** In Gnosis CTF, outcome tokens are not pre-minted upfront. Instead, users acquire outcome tokens by **splitting collateral**. For example, if a user wants to bet $10 on “Yes”, what actually happens is the user supplies $10 USDC to the ConditionalTokens contract, which in return mints 10 units of “Yes” token _and_ 10 units of “No” token (because the collateral is split into all outcome tokens). The user then typically sells the unwanted “No” side to the market maker (or effectively, they end up holding only the “Yes” side after the trade is settled). This mechanism ensures that every outcome token is always fully collateralized by USDC in the contract[\[20\]\[21\]](https://medium.com/@abiodun.toluwanii/my-polymarket-revelation-diving-into-conditional-token-frameworks-and-if-this-then-that-on-the-b410c49c2187#:~:text=,USDC%20that%20users%20put%20in). If the user only wanted “Yes”, the “No” portion goes into the AMM pool or to someone else who buys it. - The ConditionalTokens contract provides functions like splitPosition and mergePositions to handle converting collateral into outcome tokens and vice versa. At resolution time, there’s also redeemPositions which allows holders of winning outcome tokens to claim their USDC payout. We will utilize these indirectly via the market maker contract for user bets (so users might not call ConditionalTokens functions directly in our UI flow, but it’s good to know they’re there).

**2\. Deploying the Fixed Product Market Maker (AMM):** Next, we deploy the **FixedProductMarketMaker (FPMM)** contract from Gnosis’s market maker library. This contract will manage a pool of USDC (collateral) and outcome tokens for each market to facilitate trading. Key points for using the FPMM: - The FPMM is usually deployed via a **factory** that takes the ConditionalTokens contract address, the specific condition (conditionId), the collateral token address (USDC), and initial funding as parameters. Gnosis provided a FixedProductMarketMakerFactory.sol to clone new markets easily[\[22\]](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=The%20story%20behind%20util,sol). We can deploy the factory or deploy FPMMs directly for each question. - When a new market is created on our platform, we will do the following on-chain: 1. **Prepare the condition** on ConditionalTokens (as described above). 2. **Deploy or initialize an FPMM contract** for that condition. This FPMM will be linked to the conditionId and know there are 2 outcome tokens (Yes/No) for that condition. It will also reference the USDC token contract as the collateral. 3. **Provide initial liquidity:** For the AMM to start functioning, it needs an initial balance of both outcome tokens. Typically, the market creator or the platform will supply some initial USDC which gets split into equal Yes and No shares to seed the pool. For example, we might seed 100 USDC which becomes 100 Yes tokens and 100 No tokens (representing a 50/50 starting odds). These tokens are held in the AMM contract’s reserves. Alternatively, we could start with a very small seed and let the first bettor effectively set the odds. - The FPMM maintains the invariant x_y=k for the two token reserves. So if people keep buying “Yes”, its reserve decreases and “No” reserve increases, driving the price of “Yes” up (since now less “Yes” token available vs “No”). The formula for price P(Yes) in a two-outcome CPMM is P_yes = (reserve_no / reserve_yes + reserve_no) after a small trade, effectively. We can rely on the contract’s functions to handle the math. Likely the FPMM contract has a function like buy(uint outcomeIndex, uint amountIn, uint minOutcomeTokensOut) for trading. - We’ll integrate USDC_ _ERC-20 approvals_ _and transfers such that when a user swipes “Yes” (betting), the front-end will call the FPMM’s buy function (or a wrapper) to send in USDC and receive “Yes” tokens. The AMM will automatically adjust prices. The user doesn’t necessarily need to manage the tokens – they just see their bet placed and maybe their position (how much they’ve staked on each outcome). - One nuance: because Gnosis uses_ _ERC1155_ _for outcome tokens, the FPMM interacts with the ConditionalTokens contract to pull those tokens into its reserve. The user may only interact with FPMM which in turn calls ConditionalTokens internally. We will ensure to follow Gnosis’s usage patterns (the GitHub repo and any docs examples will guide the exact function calls needed to place a bet). -_ _Market closure:_\* When the prediction event’s outcome is known and the oracle finalizes the condition, the AMM trading stops (we might disable further betting either by an app-level cutoff or by withdrawing liquidity). After resolution, users will use ConditionalTokens’ redeem function to get back USDC for their winning tokens (or we can simplify and automate redemption when user opens the app post-resolution).

**3\. Oracle Integration and Condition Resolution:** As described, each condition is tied to an oracle address. To resolve a market: - If using Realitio or UMA, the flow is a bit different: for example, with Realitio, we’d set the oracle address to the Realitio contract address. The questionId might be a hash that corresponds to a Realitio question. Then, when the outcome is known, anyone can propose an answer in Realitio, it can be disputed/arbitrated if contested, and eventually Realitio’s contract will call our ConditionalTokens contract to set the payouts. Polymarket’s case with UMA was similar conceptually – they specified UMA as oracle and UMA calls back once outcome is resolved[\[15\]](https://medium.com/@abiodun.toluwanii/my-polymarket-revelation-diving-into-conditional-token-frameworks-and-if-this-then-that-on-the-b410c49c2187#:~:text=And%20here%E2%80%99s%20something%20else%20that%E2%80%99s,lose%20a%20lot%20of%20money). - **For the MVP**, we will likely use UMA. 

In summary, by the end of the smart contract setup, we’ll have: - The **ConditionalTokens** contract deployed (managing conditions and outcome tokens). - The **FPMM (market maker)** contract (or factory) deployed (managing liquidity and pricing for markets). - The ability to **create new markets** by calling our contracts (could be done by our backend or directly by users through a “create market” form in the dApp). - An **oracle mechanism** ready to resolve outcomes when due using UMA. - All contracts will be on Base mainnet and we will test them on Base’s testnet (Base Sepolia) to ensure they work with the wallet and UI before mainnet deployment.

# PHASE 2: Front-End Design
## Front-End Design: Mobile-First Swipe UX

The user interface is what will set our prediction market apart. It needs to be **engaging, simple, and mobile-optimized**. Here’s the plan for the front-end:

- **Tinder-Style Swipe Cards:** The core UI element is a **stack of cards**, each representing a prediction question. The card will show the question (e.g., _“Will Bitcoin reach $50k by Dec 2025?”_), maybe additional info like the deadline or current odds/market probability for Yes vs No. Users then swipe:
- **Right (Yes):** This initiates a bet on the “Yes” outcome. In practice, when a user swipes right, we’ll prompt (or have pre-collected) how much they want to stake (maybe a default amount or a quick slider could be set beforehand). Then we execute the **bet transaction** for “Yes”.
- **Left (No):** Similarly, swiping left places a bet on “No”.
- **Up (Skip):** Swiping up indicates the user isn’t interested in this market/question. We simply skip it without any blockchain action, and maybe move the card to the bottom of the stack or remove it. Skipping is important so users don’t feel forced to bet on every question. We will likely use a front-end library to handle the swipe gestures and physics. There are existing React packages like **react-tinder-card** that simplify implementing swipeable cards. These provide out-of-the-box support for detecting swipe direction and animating the card off the stack. Using such a library will save us time on UI implementation.
- **Mobile-First Responsive Design:** Since we target usage within a mobile app (Farcaster Base) and generally expect users on smartphones, we will design all components for small screens. This means:
- Cards will be sized to fit well on a phone screen (perhaps full-width cards that can be swiped).
- Text will be large enough to read on mobile. We’ll keep the question text concise to fit on one card without scrolling.
- Buttons and swipe targets will be touch-friendly.
- We might implement a bottom nav or simple menu for things like switching categories (e.g., filtering to only sports questions) or viewing the user’s own bets.
- We will also ensure it works on desktop (responsive web) for those who access via a regular browser, but mobile is the priority.
- **Wallet Connection & Betting Flow:** Users must connect an Ethereum wallet to bet (since bets involve USDC transfers). We’ll integrate standard Web3 wallet connectivity:
- In the **Farcaster Base app context**, authentication might already be handled. The Base mini-app environment can pass us the user’s Ethereum address or have a wallet ready. Base has a **Wallet** integration in mini-apps[\[1\]](https://docs.base.org/mini-apps/quickstart/new-apps/install#:~:text=A%20mini%20app%20is%20a,App%20using%20the%20MiniKit%20template). If that’s the case, we can use the provided signer to sign transactions under the hood.
- For web/desktop usage or if the mini app requires it, we’ll include WalletConnect and MetaMask integration. Users click “Connect Wallet”, choose their wallet, and sign a message or connect as usual. We’ll ensure we request connection to the Base network (Chain ID for Base mainnet) so that the wallet is on the correct network.
- **USDC Approval:** The first time a user tries to bet, they will need to approve the FPMM (or our contracts) to spend their USDC (ERC-20 approval). We’ll prompt this seamlessly. Possibly, we can batch the approval with the first bet to save an extra step (some wallets support gasless approvals or permit signatures – an optimization if time permits). Otherwise, the user will see one wallet prompt to approve USDC (just once), then the betting transactions thereafter.
- **Placing a Bet (Swipe Right/Left):** Upon a swipe that indicates a bet, the app will:
- **Confirm Stake Amount:** We might show a quick slider or preset buttons for how much USDC to bet (like $1, $5, $10) to let the user confirm the amount. In a rapid swipe scenario, perhaps the user can set a default stake (like always bet $1 on swipe) to truly make it one-swipe betting.
- **Execute Transaction:** We then call our smart contract – specifically, we’ll interact with the **market maker contract (FPMM)** to perform the trade. This could be abstracted in a function like placeBet(conditionId, outcomeIndex, amount). Under the hood:
  - The app calls FPMM’s function to buy the specified outcome tokens with the given USDC amount.
  - If the user’s wallet is an Externally Owned Account (EOA), this will normally trigger a wallet confirmation prompt. We aim to eliminate or minimize these prompts using gasless techniques (discussed in the next section). Ideally, after the initial approval, swiping right/left results in **no additional pop-ups** – the bets happen seamlessly and the UI immediately shows the updated state.
- **Update UI Optimistically:** To keep the app snappy, we will update the UI as soon as the swipe is made, without waiting for transaction confirmation. For example, after swiping “Yes”, we can visually indicate that **“You bet Yes with $X”** and maybe show the new odds or the user’s position. We will of course handle failures (if a transaction fails or is reverted, we should notify the user and perhaps refund their view of the tokens).
- **Next Card:** The card that was swiped on is removed from the stack, revealing the next prediction. This immediate cycling keeps users engaged – they can quickly go through a series of predictions, betting on those they care about, skipping others.
- **Displaying Market Data:** On each card (question), it’s useful to show some stats to inform the user’s decision:
- **Current odds or probability:** Based on the AMM price, e.g., “Yes: 70% / No: 30%” probability as implied by current bets. This can simply be derived from the token reserves in the AMM (or via a view function the contract provides). We will fetch this periodically or whenever the user views the card.
- **Total pool or volume:** e.g., show how much USDC has been staked in total on that question (liquidity size) to indicate popularity.
- **Time remaining:** show the deadline or lock time for the market (after which betting stops and one must wait for resolution).
- Possibly **category tags** or who created the market, etc., if space permits.
- **User-Created Markets UI:** Since users can create their own questions, we’ll include a simple form in the app: _“Create a Prediction Market”_. This form would let the user input:
- Question text (e.g., “Will X happen by Y date?”).
- Category (to help others discover it).
- An expiration date (deadline for the event).
- Choose an oracle or resolution source (for MVP, maybe this is just fixed to “Platform will resolve” or a dropdown of known oracles like “Chainlink price” or “Admin”).
- Perhaps initial odds or initial liquidity contribution (if they want to fund the market). When they submit, the app will call our backend or directly trigger contract calls to create the condition and market maker as described earlier. This likely will be a more advanced action, so if time is short, we might deprioritize the _UI for market creation_ (maybe only allow it via an admin interface initially). But it’s a key feature to highlight even if rough.
- **Farcaster Social Features:** Because we plan to integrate with Farcaster, we might include social hooks such as:
- Share a market: e.g., a button to “Share to Farcaster” that posts the question and a link to the mini-app card, inviting friends to bet.
- Show Farcaster profile info if available: If the mini-app provides context of the user’s Farcaster username, we could display “Hi, @alice! Here are today’s predictions…” to personalize.
- We have to follow Farcaster mini-app guidelines for UI (to fit nicely in their client). That means probably using their design kit for modals, etc., and ensuring the app’s pages are lightweight (Next.js with static generation or simple pages).

Overall, the front-end will be built with **React/Next.js** for rapid development. We will utilize component libraries for speed (e.g., use a UI kit or simple CSS frameworks to avoid spending time on styling basics). The main custom work is on the swipe interface and Web3 integration: - We’ll use **ethers.js or web3.js** to interact with contracts. Given Next.js, ethers.js is a good choice for its simplicity. - Use **WalletConnect** to support mobile wallets if not in the Base app context. - Use **Coinbase Wallet SDK** if we want to directly integrate with Coinbase Wallet (since Base is Coinbase’s chain, many users might use Coinbase Wallet). - The app will maintain state of the markets, possibly fetching from the blockchain on load (for e.g., list of active markets, their odds, etc.). We might set up a simple subgraph or just query the contracts directly for now (the number of markets in 15 days likely small).

**Emphasis on UX:** The hallmark of our design is that **betting feels as easy as browsing a social feed**. Traditional blockchain apps make you confirm every transaction and can be slow; we want to hide that complexity. By planning for **gasless transactions**, enabling **quick swipes**, and integrating into a social app, we are drastically lowering the barrier to participation. New users should be able to start betting without even knowing much about crypto (beyond maybe acquiring some USDC). If they have to get USDC, Base’s integration might allow an easy fiat onramp or bridging in-app, which we can point them to if needed.

In summary, the front-end will combine **engaging swipe interactions** with **smooth Web3 onboarding** to make the prediction market enjoyable and accessible. Next, we address how we’ll achieve the gasless, one-swipe user flow technically.

## Gasless Transactions and Batched Swipes on Base

One of the biggest UX improvements we want is to eliminate the need for users to manually confirm every bet transaction. In a normal scenario, each swipe (bet) would trigger a MetaMask confirmation and require the user to pay a gas fee in ETH. This would make swiping through multiple questions very tedious. Our solution is to leverage **gasless transactions and transaction batching** on Base:

- **Base Paymaster (Account Abstraction via ERC-4337):** Base supports **ERC-4337 Account Abstraction**, which enables gas sponsorship. Coinbase’s developer platform provides a **Paymaster service** that can sponsor user operations (transactions) up to certain limits[\[3\]](https://docs.base.org/cookbook/go-gasless#:~:text=Base%20transaction%20fees%20are%20typically,The%20Paymaster%20allows%20you%20to). By setting up a Paymaster, our dApp can pay the gas on behalf of users. In practice, the user would sign a transaction intent, and a **Bundler** (run by the Base infrastructure) will include it on-chain, with the Paymaster paying the gas in ETH. Base offers up to $15k worth of gas sponsorship per month for free to developers on mainnet[\[24\]](https://docs.base.org/cookbook/go-gasless#:~:text=%2A%20Batch%20multi,unlimited%20on%20testnet), which is great for a beta launch. We will:
- Register our contract methods that can be gas-sponsored (likely the betting function on the FPMM, and perhaps the USDC approval).
- Use the Coinbase Cloud Developer Portal to get an API key and Paymaster setup for our app (as per Base docs).
- On the front-end, instead of sending a regular transaction via eth_sendTransaction, we will create a **UserOperation** (ERC-4337 style) and send it to the bundler RPC provided by Base. This user op will contain the call to our contracts and the Paymaster info so it’s subsidized.
- The result: users won’t need ETH for gas on Base, and they won’t see a gas deduction. To them, it feels like free transactions. **“Gasless”** in the user experience sense.
- Moreover, the Paymaster allows **batching multi-step transactions**[\[3\]](https://docs.base.org/cookbook/go-gasless#:~:text=Base%20transaction%20fees%20are%20typically,The%20Paymaster%20allows%20you%20to). If a user’s action actually requires multiple contract calls (e.g., maybe approve USDC + bet, or betting on multiple markets), we can bundle them into one atomic user operation. This means one signature from the user can do multiple things on-chain.
- **Meta-Transactions (Alternative Approach):** If for any reason the Base Paymaster approach is difficult to implement in time, another route is using traditional **meta-transactions with a relayer**. This involves a trusted server (our backend) accepting signed messages from users and then broadcasting the actual transactions. For example:
- We could have the user sign a message like “I authorize betting YES on market X with Y USDC.” Our backend verifies the signature and then sends the transaction to the FPMM contract (paying gas itself).
- The smart contract (we might need a forwarder contract) would recognize the original signer so the bet is attributed correctly (using ecrecover or an EIP-712 signature that encodes the action). This pattern is essentially what the **Gas Station Network (GSN)** does – a relayer pays the gas, and the contract repays or trusts them[\[25\]](https://docs.openzeppelin.com/learn/sending-gasless-transactions#:~:text=Enter%20meta,a%20wallet%20or%20own%20Ether). OpenGSN v2 could be integrated if time permits, but running our own simple relayer might be faster for a MVP.
- The meta-transaction approach achieves a similar outcome: **users sign once, and then bets execute without further prompts**, as the relayer handles it. The downside is we (the developers) need to manage the relayer infrastructure and fund the gas, but given Base’s low fees this is manageable in the short term.
- **Batching Multiple Swipes:** The concept of batching is that a user could swipe on several questions and we combine those actions into fewer on-chain transactions. There are a couple ways to approach this:
- On the front-end, we could allow the user to queue up a few bets (e.g. swipe through 5 questions, all those intents are signed/stored) and then periodically send a batch to the chain. However, this introduces complexity in handling state (what if the first 2 succeeded and 3rd failed, etc.). It might also reduce real-time feel.
- A better approach with account abstraction is to utilize a **smart contract wallet** for the user that supports multi-call. If each user had a simple smart wallet (4337 account) that can bundle calls, the user could sign one userOp that contains multiple calls – e.g., call market1.buy(), market2.buy(), market3.buy() in one operation. This would execute all bets in one transaction (all-or-nothing). Setting this up in 15 days might be too much (deploying a wallet per user is heavy).
- Alternatively, we focus on **one-swipe-one-transaction**, but ensure it’s gasless and fast. With the Paymaster, each swipe can be sent immediately and in parallel without waiting for user approvals. The user could literally rapid-fire swipe through 10 cards, and behind the scenes 10 transactions get sent via the bundler. They might land on-chain a few seconds apart, which is fine. The important part is the user isn’t stopped to confirm or pay for each one.
- We will implement at least the capability to do _two-step batching_: for instance, combine the “approve USDC” and the first bet into one transaction (so the first bet feels like a single action). Base’s paymaster can handle multi-step flows like that[\[3\]](https://docs.base.org/cookbook/go-gasless#:~:text=Base%20transaction%20fees%20are%20typically,The%20Paymaster%20allows%20you%20to).
- **User Signature & Security:** Even with gasless, the user still needs to **sign** the transaction (to authorize spending their USDC and such). In an EOA scenario, the wallet (e.g. MetaMask) will prompt for a signature of the userOperation or meta-tx. This is typically a different prompt than a normal transaction – e.g., MetaMask might show “Do you want to sign this message?”. We will explain to users that this signature authorizes the app to execute the bets. If using the Base app, the signing might be transparent or one-click since it’s all integrated. We want to make sure this process is as smooth as possible (perhaps the user can sign a “session” that lasts for a few minutes or a set of actions).
- **Gas Funding:** We as developers must plan to fund the gas costs. Base’s gas is paid in ETH. We’ll keep an ETH balance in the Paymaster or relayer account. Given Base’s low fees (~$0.01 or less per tx), even a few hundred transactions won’t break the bank. And with Coinbase’s sponsorship up to $15k, we are unlikely to exceed that during a MVP demo or early usage.

In summary, **by using Base’s Paymaster and/or meta-transaction relayers, we ensure that users do not need to hold ETH or click confirm for each swipe**. This makes the prediction market truly feel like a web2 app: the crypto complexity stays under the hood. It addresses a common onboarding hurdle where new users get confused by gas or run out of ETH[\[26\]](https://docs.openzeppelin.com/learn/sending-gasless-transactions#:~:text=Anyone%20who%20sends%20an%20Ethereum,major%20hurdle%20in%20user%20onboarding)[\[25\]](https://docs.openzeppelin.com/learn/sending-gasless-transactions#:~:text=Enter%20meta,a%20wallet%20or%20own%20Ether). Our platform will **abstract gas fees away**, possibly even branding it as “free swipes” or “no gas needed” in user messaging.

**Example Flow with Gasless:** A new user joins via Farcaster mini-app -> connects wallet -> buys or bridges some USDC -> starts swiping bets. They swipe “Yes” on 5 different questions in one session. They see instant feedback for each swipe. In the background, 5 transactions are submitted via the paymaster. After a minute, all those bets are confirmed on-chain and their positions are recorded, without the user having to do anything else. This is the target experience.

## Development Timeline and Strategy

With only **15 days** to build and deploy, time management is critical. Below is a rough breakdown of how we’ll tackle the project in phases, focusing on parallelizing where possible:

- **Days 1-3: Setup and Smart Contract Base** – We will spend the first couple of days setting up the project repo, tools, and getting the Gnosis contracts deployed on a testnet. This includes:
- Cloning the Gnosis Conditional Tokens and Market Maker repositories. Install dependencies, and attempt a local deployment (perhaps on Hardhat or Foundry) to ensure we understand the process.
- Modify deployment scripts to target Base **Sepolia testnet** (Base has a testnet environment akin to Goerli) for initial trials.
- Deploy ConditionalTokens contract and a sample FPMM on testnet. Write a quick test or script to create a dummy market (e.g., “Will it rain tomorrow?”) and simulate a few bets to verify the contracts work as expected on Base.
- If any solidity adjustments are needed (Solidity version compatibility or Base-specific config), handle those early.
- Also, define how we will do the oracle for testing – maybe write a simple function to call reportPayouts manually.
- **Days 4-6: Front-End Skeleton & Wallet Integration** – In parallel, start the Next.js app:
- Use npx create-onchain --mini (Base’s MiniKit CLI) to scaffold the mini-app project[\[27\]](https://docs.base.org/mini-apps/quickstart/new-apps/install#:~:text=Copy). This gives us a template integrated with Base app context.
- Implement wallet connect logic and test connecting to our deployed testnet contracts. Ensure we can read data (like list of markets, odds) from the contracts via ethers.js.
- Build a basic page that lists questions and a detail view for a question as a placeholder (before the swipe UI is fully implemented). This ensures the data flow from blockchain to UI is working.
- If Farcaster context is available, test getting the user’s Farcaster ID or profile (just to confirm the mini-app integration).
- **Days 5-8: Core Functionality – Betting Logic** – During this time we focus on making sure a user can actually place a bet and the contracts respond correctly:
- Implement the swipe card component. Start with one card at a time for simplicity – e.g., show the first question with Yes/No buttons (for easier debugging than actual swipes). Hook those buttons up to call a betting function.
- Write the placeBet() function in the front-end which:
  - Checks if user has approved USDC; if not, calls approve() (and maybe wraps it with our gasless mechanism).
  - Calls the FPMM contract’s method to trade. Use a small amount for testing, e.g., bet 1 USDC.
  - Wait for confirmation and update state.
- Test this end-to-end on Base testnet: the USDC (we’ll use a test USDC or any ERC-20 on testnet) should move from user to contract, and the contract’s internal state (outcome token balance) updates. We should see the odds shift if we query again.
- Implement skipping and loading next questions. Possibly set up a dummy list of questions in the front-end state for now.
- **Integrate gasless**: By day 7 or so, attempt to integrate the Base Paymaster. This might involve:
  - Using the Coinbase API to get a paymaster-enabled RPC URL or bundler.
  - Adjusting ethers provider to use eth_sendUserOperation instead of eth_sendTransaction (depending on how they implement it).
  - Testing a gasless call on testnet (maybe sponsor a simple transaction to see it works).
  - If stuck, implement a fallback meta-tx: maybe deploy a simple GSN Forwarder contract on testnet and have our front-end sign messages to it. This is a backup if direct 4337 proves complex.
- By end of Day 8, we want to have **a working prototype on testnet**: You can connect a wallet, see a question, swipe to bet yes or no, and see the result update without manual confirms (maybe one confirm if not fully gasless yet).
- **Days 9-11: Expand Features & Polishing** – With the core in place, we expand and refine:
- Implement the real swipe gesture (integrate the react-tinder-card or similar and test on mobile browsers).
- Create a list or feed of multiple active markets. This could be fetched from an index (if we maintain an array of created markets in a contract or simply have the backend feed it). We might maintain an off-chain list of questions for simplicity, since indexing on-chain events might be heavy for an MVP. Alternatively, deploy a simple registry contract where each new market is recorded.
- Add UI elements: display current odds on each card, display user’s current balance of USDC and maybe any winnings pending.
- Ensure the UI looks presentable: apply some styling, maybe a color scheme. Keep it simple but not ugly.
- Work on the **Create Market** form if time allows. Even an admin-only creation is fine (so we can showcase user-generated content, even if we manually use the form as “user”).
- Integrate category filters or tags (not crucial, but if we have multiple categories, a simple filter menu helps; can be done if ahead of schedule).
- **Days 12-13: Oracle and Resolution Testing** – We should simulate a full cycle of a market:
- Pick a test market that “expires” (we can define an end time in our UI for when no more bets are allowed).
- After expiry, call the oracle function (if manual, just use our account) to report the outcome on testnet.
- In the UI, detect that the market is resolved and allow the user to claim winnings. We might add a “Claim” button that calls ConditionalTokens redeemPositions for them (or have the contract auto-transfer on resolution if possible).
- Verify that winners get their USDC back plus profit, and losers’ position tokens are worthless.
- This end-to-end test ensures our oracle integration works and the payout flows are correct.
- **Day 14: Deployment to Base Mainnet** – Assuming tests are green, we prepare for mainnet:
- Deploy the ConditionalTokens and FPMM (factory) contracts on Base mainnet. We’ll need to fund the deployer with some ETH on Base. Verify addresses.
- Point the front-end config to mainnet contract addresses and the mainnet USDC token address (and ensure the user’s wallet is on Base mainnet when connecting).
- Set up the Paymaster for mainnet (Coinbase might require enabling it for mainnet explicitly, and ensuring our daily limits etc. are in place).
- For initial markets, perhaps create a few seed markets on mainnet so the app isn’t empty. We can do this via our UI or a quick script (e.g., “Will ETH price be above $2000 on X date”, “Will Team A win tonight’s match”, etc., covering different categories to showcase).
- **Day 15: Final Testing, Buffer, and Presentation Prep** – Use this last day to:
- Do a final run-through of the user flow on mainnet with a fresh wallet. Iron out any last-minute bugs or UI quirks.
- Ensure all important actions (betting, creating market, claiming) have appropriate success/failure messages and that errors (like insufficient balance) are handled gracefully.
- Write documentation (for the MVP submission) explaining how the app works, the design choices, and instructions for judges/users.
- If this is a MVP project, prepare the demo presentation, screenshots, etc. Focus on the unique selling points: the swipe UX and the seamless betting experience made possible by the tech stack.

Throughout the development, we’ll keep an eye on **scope management**. If something is taking too long (for example, if the oracle integration with Realitio is complex), we’ll switch to a simpler method (like manual resolution) to keep momentum. The goal in 15 days is a functional product, even if some aspects are centralized or simplified at first.

## Conclusion and Future Outlook

Building a prediction market in 15 days is ambitious, but by leveraging existing frameworks and focusing on core functionality, it’s feasible. We chose Gnosis’s Conditional Token Framework because it provides the **fundamental building blocks for prediction markets** – from outcome tokenization to proven market-making algorithms – significantly accelerating our development[\[12\]](https://medium.com/thecapital/exploring-the-gnosis-conditional-token-framework-27744fca2558#:~:text=Framework). We’re combining that with the **Base network’s modern features** (L2 scalability and built-in gas abstractions) to ensure the dApp is not just quick to build, but also fast and cheap for users to run. The envisioned platform marries _decentralized finance_ with a _familiar swipe-based UX_, lowering the barrier for ordinary users to participate in prediction markets.

In this deep dive, we covered how each piece will be implemented: smart contracts for creating and trading on prediction events, an oracle for settling outcomes with real-world truth, a mobile-friendly interface for an engaging user experience, and gasless transactions to hide blockchain friction. We also outlined a tight schedule to get it all done in two weeks.

By the end, we expect to have a live **“swipe-to-bet” prediction market on Base mainnet** where users can wager USDC on topics ranging from crypto prices to local events. In the future, we can enhance this foundation with features like a reputation system (for top predictors), community moderation of markets, integration with social feeds (so outcomes of bets can be shared), and more decentralized oracles (so that the platform can fully trustlessly resolve any question). We could also add multi-outcome markets (not just Yes/No) using the same Conditional Tokens framework.

Most importantly, this project has the potential to make prediction markets **fun and mainstream-friendly**. By simplifying the UX to a swipe and abstracting away the blockchain complexities, we align with how Web3 dApps need to evolve for mass adoption. Participants can focus on their knowledge and opinions about events, while the dApp seamlessly handles all the Web3 heavy lifting in the background – from trading logic to token settlement to gas fees[\[3\]](https://docs.base.org/cookbook/go-gasless#:~:text=Base%20transaction%20fees%20are%20typically,The%20Paymaster%20allows%20you%20to).

In short, our strategy is: **use powerful DeFi backend tech, but present it with a Web2-level user experience.** If successful, this MVP project could evolve into a popular mini-app on Farcaster/Base, engaging users with friendly competition and potentially crowd-sourced insights into future events. Prediction markets have been touted for their ability to aggregate wisdom; with our social, gamified approach, we aim to also aggregate engagement and make it enjoyable.
